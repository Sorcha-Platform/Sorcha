Sorcha, from first principles.

A calm introduction to how Sorcha works — the core idea, the moving parts, and the standards underneath — before you head into the API reference or the self-hosting guide. Read this first; then go deeper.

What Sorcha is

Sorcha is open-source cryptographic proof infrastructure for multi-party workflows. It replaces asserted trust — an operator's word that something happened — with verifiable proof that anyone can check. It issues and verifies verifiable credentials and orchestrates the signed, tamper-evident workflow around them. It is built on .NET 10 and .NET Aspire, MIT-licensed, and self-hostable with Docker.

The core idea

Most systems ask you to trust the operator. Sorcha asks you to trust the evidence. Every action is signed by the participant who took it, recorded in an append-only, Merkle-linked register, disclosed only to the parties entitled to see it, and independently verifiable by anyone. The same four steps run under every workflow.

01

Sign

Each participant holds their own keys. Every action is signed by the person or organisation who took it — accountability is built in, not bolted on.

02

Record

Signed actions are written to an append-only register, each entry Merkle-chained to the last. Nothing can be altered or quietly removed.

03

Disclose

Each party sees only the fields they're entitled to — and each party's data is encrypted to a key only they hold (per-recipient key wrapping). The platform cannot read what it was not given access to.

04

Verify

Any party can check the signatures and the chain themselves. Trust comes from the evidence, not from us.

Key concepts

The vocabulary worth knowing before the deeper docs.

  • Blueprint — a workflow definition: the participants, the actions they can take, and the order things happen in. Authored as JSON or YAML and published before any work begins.
  • Register — the append-only ledger a workflow's actions are written to. Each entry is Merkle-linked to the one before, so the history is tamper-evident.
  • Wallet — holds a participant's keys, signs their actions, and holds the verifiable credentials issued to them. Keys derive from a hierarchical-deterministic seed (BIP-32/39/44).
  • Participant / Peer — a participant is a party in a workflow (a person or organisation); a peer is a node in the decentralised network that replicates registers so no single party can erase them.
  • Credential — a verifiable credential: a signed, tamper-evident claim a holder can present and a verifier can check, following W3C Verifiable Credentials 2.0 and the SD-JWT VC profile.
  • Presentation — the act of showing one or more credentials to a relying party, who verifies them directly (OpenID4VP).
  • Disclosure — selective disclosure: each recipient sees only the fields they are entitled to, and that data is sealed to a key only they hold.
  • did:sorcha — Sorcha's decentralised identifier method, used to name and resolve participants and their keys.

The system at a glance

Eight single-responsibility services, each doing one job. They compose into the platform; the API Gateway is the only part the outside world talks to directly.

  • Blueprint — workflow definitions.
  • Wallet — keys, signing, and credential holding.
  • Register — append-only Merkle ledgers.
  • Validator — quorum consensus over what is admitted to a register.
  • Peer — decentralised replication across the network.
  • Tenant — multi-tenancy, identity, and access.
  • API Gateway — the single external surface in front of the services.
  • HAIP — the boundary to the OpenID4VC wallet ecosystem.

Standards and cryptography

ML-DSA (FIPS 204) ML-KEM (FIPS 203) SLH-DSA (FIPS 205) BIP-32/39/44 Merkle + SHA-256 OpenID4VCI OpenID4VP SD-JWT VC W3C VC 2.0 did:sorcha

Signing defaults to ML-DSA (FIPS 204), a post-quantum signature scheme, with ML-KEM (FIPS 203) for key encapsulation and SLH-DSA (FIPS 205) primitives also present. Wallets derive keys with BIP-32/39/44; registers chain their entries with Merkle dockets and SHA-256. At the wallet boundary the HAIP service speaks OpenID4VCI, OpenID4VP and SD-JWT VC, issuing W3C Verifiable Credentials 2.0 named with the did:sorcha method. The Developers page carries the full list and the rationale.

Design principles

  • Trust from evidence, not operators. Verification rests on signatures and the chain, not on trusting whoever runs the system.
  • Open standards over proprietary lock-in. Every protocol and primitive is a published standard you can implement against.
  • Post-quantum by default. The default signing path is ML-DSA, so records stay verifiable as cryptography moves on.
  • Participant-held keys. Each party holds their own keys and signs their own actions; the platform never signs on their behalf.
  • Rehearse before go-live. A workflow is rehearsed and validated before it can be published and run for real.
