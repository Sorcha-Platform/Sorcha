> **2026-08-20 — HAIP issued SD-JWT VCs with no type identifier (#1540), and the OID4VP round trip now completes.** SD-JWT VC §3.2.2.1 makes `vct` the credential's **sole** type claim and REQUIRES it, and `HaipCredentialMinter` never wrote one: `credentialType` arrived at both mint overloads and was spent on the `sub` string and a log line. > **2026-08-18 — A suspended credential was ACCEPTED after the purposes were split (PR #1495).** A regression introduced by #1491 and caught while sizing the read-side gap, before it reached n1. Splitting revocation and suspension gave a credential TWO `credentialStatus` entries, but the reader kept returning ONE reference and preferred the revocation entry — so a credential suspended but not revoked had only its (clear) revocation bit checked and passed verification. Before the split, suspension set the revocation bit, so it was refused for the wrong reason but refused: **fixing the reason removed the enforcement.** The giveaway was inside the change itself — `ExtractStatusReferences` had **no callers**, a helper documented as being "for callers that must evaluate every purpose" and never wired to one, which is the dead-predicate shape this codebase has hit repeatedly. Fix: `IssuerContext` gains `Statuses` (all declared references, `Status` retained as the primary), `TrustEvaluator` iterates every reference and refuses on the first set — naming the purpose in the message so an operator can tell a suspension from a revocation in the log — and the SD-JWT handler populates the full set; falls back to the single `Status` so the mdoc handler is unchanged. Mutation-verified end to end through a REAL signed SD-JWT carrying one entry per purpose (the mint factory gained an optional `credentialStatusClaim`, since it previously only supported the IETF single-status form — part of why this went unnoticed). Engine 618, Blueprint.Service 1148, Haip.Service 123. ⚠ **Still open**: the failure reason remains `TrustFailureReason.Revoked` for both, so a suspension is REPORTED to verifiers as a revocation. Distinguishing them end to end needed `StatusListBit` + `TrustFailureReason` widened — **done as Feature 192** (`specs/192-credential-status-reporting/`, gates A1/B2/C1/D2), which retired `StatusListBit` for `CredentialStatusValue` and fixed the IETF read side that #1492 had left collapsing `0x01` and `0x02` together.

> **2026-08-18 — Status lists brought into conformance with BOTH specs (#1482 continued; PRs #1490-#1493).** Three further defects, each a layer under the last. **(1) A captive dependency crash-looped n1 on deploy** — `StatusListLedgerReconciler` took the SCOPED `IRegisterServiceClient` while consumed by the singleton `StatusListManager`; production DI validation refuses that at startup. Rolled back in minutes, fixed forward with `IServiceScopeFactory` (**PR #1490**). **Nothing caught it**: unit tests `new` the types and bypass DI, and the integration suite dies earlier on `ServiceAuth:ClientId not configured` without the compose stack — verified by reintroducing the bug and watching that suite report the same env error either way. Guard added (`StatusListDependencyLifetimeTests`, ValidateScopes+ValidateOnBuild), mutation-tested by making the mirrored graph captive, because such a test passes vacuously if those options are ever dropped. **(2) Suspension was written to the REVOCATION list (PR #1491).** W3C is explicit — `revocation` "is not reversible", `suspension` "is reversible" — and Sorcha hardcoded one list with purpose `revocation` and set that single bit for both. So a merely SUSPENDED credential was advertised to every verifier as REVOKED, and reinstate CLEARED a revocation bit the spec says can never clear. Now a list per purpose sharing one index, issuance emitting one `BitstringStatusListEntry` per purpose (array form only when a suspension list exists, so single-purpose credentials keep the shape existing verifiers read), and the SD-JWT handler reading `credentialStatus` as object OR array. The reconciler decides by STATUS WORD not by the list id an event names — everything written between #1487 and #1491 names the revocation list, suspensions included. **(3) The IETF rail declared `bits: 2` over a 1-bit array (PR #1492).** IETF models suspension as a VALUE (`0x00` VALID / `0x01` INVALID / `0x02` SUSPENDED) inside ONE list, where W3C uses a list per purpose — so the IETF view must be a PROJECTION of the stored W3C lists, not a relabelling. Declaring `bits` is a claim about byte layout: a conformant reader takes entry N from bits 2N..2N+1, so revoking index 1 made index 0 report not-valid, inventing a status for a credential nobody touched — and our own `IetfTokenStatusListChecker` honours `bits`, so it misread our own output. `IetfStatusListPacker` now builds a real 2-bit array (revocation outranks suspension, terminal in both specs); a revocation-only list stays 1-bit and passes through. **#1491 and #1492 are the same mistake at two layers** — treating suspension as a variant of revocation, once as a shared bit and once as a shared byte layout. Spec comparison, verbatim wording and the resulting rules folded into the `verifiable-credentials` skill (**PR #1493**). ⚠ **Known gap, deliberately open:** `IetfTokenStatusListChecker.ReadBit` collapses a multi-bit entry to `Set`/`NotSet`, so on the READ side SUSPENDED and INVALID are indistinguishable; `StatusListBit` has no third state and widening it changes the verification surface. ⚠ **n1 carries #1490 (live-proven: revoke, restart, bit survives, credential still refused) but NOT yet #1491/#1492.**

> **2026-08-18 — Credential revocation made durable, auditable and cross-node (#1475 / #1482 / #1483).** Live-running the revocation walkthrough after #1475 opened a path nothing had ever exercised, and it exposed three further layers. **(1) A revocation never reached the ledger** — 33 transactions on the CyberEssentialsUac register after ~5 revocations, all Actions, ZERO status changes, and zero submit successes or failures in the whole blueprint-service log. > **2026-08-17 — #1469: `formatMaximum` date bounds are now ENFORCED by the validator (PR #1480, open).** Measured live on n1 first: the validator enforces every standard keyword the core primitives use — `format: date` **including calendar validity** (`2026-02-30` refused), `format: email`, `minLength`, `maxLength`, all with precise `VAL_SCHEMA_004` messages — and **silently accepted `dateOfBirth = 2035-06-15`, sealing it into a docket**, because `formatMaximum` is not a JSON Schema keyword and unknown keywords are annotations. `DateOfBirth.v1`'s description claimed the validator rejected future dates; it never had. **Stuart's ruling settles the fork this issue carried: "the schema and the data are the truth; display is for humans — render-only is stupid as it's about validation, and date ranges must be enforced validation."** So the competing proposal to rename the keyword `x-format-maximum` (which would have made the bound permanently renderer-only) is **dead**. Consequently an explicit `2020-12` is now **UPGRADED** to the superset, a deliberate reversal of #1473's "never overwrite", or every existing blueprint would keep ignoring its own declared bounds; other drafts are still left untouched. Scope is narrow by design: non-string → `type`, non-date string → `format` (one defect, one error), unresolvable bound **fails CLOSED**, bounds inclusive, `today-18Y` age gates now work. `SorchaDateTokenResolver` moves `Sorcha.Validator.Core` → `Sorcha.Blueprint.Models` so both evaluation sites reach it — **it had ZERO production consumers**, which is the bug in one line. **Both evaluation sites move together** (`ValidationEngine` + the `Blueprint.Engine.SchemaValidator` mirror); a THIRD mirror in `Sorcha.Register.Models.Tests` that had silently stopped matching production at #1473 is brought back into line. > **2026-07-30 — Catch-up security review remediation: B2+ (caller-organisation binding) SHIPPED.** The invitation finding (#1292) generalised: **six** org-scoped route groups in the Tenant Service had ZERO caller-org binding, and no handler compared the caller either. `RequireAdministrator` is literally `RequireRole("SystemAdmin","Administrator")` and never inspects `org_id`; `RequirePlatformAudience` adds a tier check, not an organisation one. > **2026-07-30 — Catch-up security review remediation: B2+ WAVE 2 (remaining org-scoped groups) SHIPPED.** The five groups deliberately left out of wave 1 were each assessed individually; **all five needed the caller-org bind**, and one is the most serious of the entire set. **`IdpConfigurationEndpoints`** (`/api/organizations/{orgId}/idp`) decides HOW USERS AUTHENTICATE into an organisation — an administrator of org A could repoint org B's identity provider at an IDP they control, i.e. **account takeover of org B**. **`RegisterSubscriptionEndpoints`** read routes carried plain `.RequireAuthorization()` — not even a role check — so **any** signed-in principal, including a citizen, could enumerate any organisation's register subscriptions.
