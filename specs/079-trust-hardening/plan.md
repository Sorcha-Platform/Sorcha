# Implementation Plan: Transaction Receipts, Merkle Inclusion Proofs & Revocation Transactions

**Branch**: `079-trust-hardening` | **Date**: 2026-03-31 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/079-trust-hardening/spec.md`

## Summary

Three trust-hardening primitives for the Sorcha distributed ledger: (1) cryptographically signed transaction receipts generated during docket sealing, (2) standard Merkle inclusion proofs for lightweight offline verification, and (3) first-class revocation transactions that supersede previously sealed transactions. All operate on the transaction envelope (not encrypted payloads), maintaining full FLE compatibility. The implementation extends existing infrastructure — MerkleTree, Validator.Core, DocketDistributor, and Register Service endpoints.

**Constraints**: Offline-capable verification (Validator.Core must work without network), FLE-compatible (envelope operations only)
**Scale/Scope**: Typical dockets 10-1000 transactions, proof paths 4-10 steps (log2), receipts immutable append-only

## Key Technical Decisions

### Receipt Generation Flow

```
DocketDistributor.SubmitToRegisterServiceAsync()
  └── WriteDocketAsync() succeeds
       └── ReceiptGenerator.GenerateReceiptsForDocket(docket)
            ├── MerkleTree.GenerateAllProofs(txHashes) — O(n log n)
            ├── For each tx: build receipt with proof path
            ├── Sign each receipt with Validator system wallet
            └── POST /receipts/batch to Register Service
                 ├── Store in MongoDB receipts collection
                 └── Publish receipt:generated to Redis Stream
                      └── RegisterEventBridgeService → SignalR push
```

### Revocation Validation Flow

```
ValidationEngine.ValidateTransactionAsync()
  └── TransactionType == Revocation?
       └── ValidateRevocationAsync(transaction)
            ├── Parse RevocationPayload from payload
            ├── Query Register: target tx exists? Not already revoked?
            ├── Check: target is not itself a Revocation tx
            ├── Authority check:
            │   ├── sender == original tx sender? → authorised
            │   └── else: reconstruct roster → Owner/Admin? → authorised
            ├── Validate reason enum + supersededByTxId consistency
            └── Standard signature + sequence validation
```

### Offline Verification Flow

```
BundleVerifier.VerifyBundle(bundle, validatorPublicKeys)
  ├── Check 1: CredentialSignatureValid
  │   └── Verify VC issuer signature
  ├── Check 2: InclusionProofValid
  │   └── MerkleTree.VerifyMerkleProof(txHash, root, proofPath)
  ├── Check 3: ReceiptSignatureValid
  │   └── Verify validator signature over receipt content
  └── Check 4: RevocationStatusAtExportTime
       └── Check bundle.RevocationStatus.Status == Active
            └── If not: include warning about stale status
```
