# Phase 1 Data Model: AI Discoverability & Machine-Readable Marketing

**Feature**: 117-ai-discoverability

This feature ships several **wire-format records** (over-the-wire shapes describing the platform's API surface and discovery surface) and **document records** (Markdown / plain-text files with structured frontmatter or table shape). It does not introduce any persistent storage entities.

---

## Wire-format records

### 1. OpenAPI 3.1 document (served, generated)

Generated by `Microsoft.AspNetCore.OpenApi` from endpoint metadata. Served at `/.well-known/openapi.json` (and `/.well-known/openapi.yaml` as the YAML variant).

**`info` block additions** (injected by `OpenApiInfoTransformer`):

```json
{
  "info": {
    "title": "Sorcha API",
    "version": "<assembly informational version>",
    "description": "Sorcha — cryptographic proof infrastructure for multi-party workflows. Produces evidence (wallet signatures, Merkle dockets, immutable register entries) that any party can verify independently. The verified-data layer for AI systems making automated decisions, and the workflow infrastructure above HAIP / EUDI / GOV.UK Wallet ecosystems. Authoring source: docs/strategic-context.md.",
    "contact": {
      "url": "https://github.com/Sorcha-Platform/Sorcha"
    },
    "x-mcp-server": "https://<host>/.well-known/mcp.json",
    "x-standards": [
      "BIP32", "BIP39", "BIP44",
      "ML-DSA (FIPS 204)",
      "OpenID4VCI", "OpenID4VP", "HAIP 1.0",
      "W3C VC Data Model 2.0",
      "IETF Token Status List 2024 (RFC 9972)",
      "W3C Bitstring Status List",
      "DID (W3C)",
      "OAuth 2.0"
    ]
  }
}
```

**Per-endpoint metadata required**:

- `operationId` — PascalCase, `<Resource><Verb>` (e.g. `WalletGet`, `CredentialIssue`, `RegisterStatusGet`).
- `summary` — one sentence.
- `description` — what the operation does, when to call it, what it returns.
- `tags` — service name (`Wallet`, `Credential`, `Register`, `Blueprint`, `Tenant`, `Peer`, `Validator`, `Haip`, `Health`, `System`, `Dashboard`, `Monitoring`, `Documentation`, `Client`).
- (optional) `x-status: "partial"` — when the endpoint specification is incomplete.

**Per-schema-property requirement**:

- `description` — non-empty string. Sourced from XML doc comments (`/// <summary>`) when present; from `[Description("...")]` attribute otherwise.

**Per-credential-issuance / wallet-signing endpoint requirement**:

- At least one `example` value for the request body and one for the success response.

### 2. MCP server manifest (served from configuration)

Wire format: JSON, served at `/.well-known/mcp.json`, validated against `contracts/mcp-manifest.schema.json`.

```json
{
  "$schema": "https://<host>/contracts/mcp-manifest.schema.json",
  "name": "sorcha-mcp",
  "version": "<canonical platform version>",
  "description": "MCP server for Sorcha — cryptographic proof infrastructure for multi-party workflows. Tools drive verified credential issuance, blueprint design, and participant actions; every action signed, every state transition ledger-recorded, every disclosure cryptographically bounded.",
  "transports": [
    {
      "type": "stdio",
      "command": "dotnet",
      "args": ["run", "--project", "src/Apps/Sorcha.McpServer"]
    },
    {
      "type": "http+sse",
      "url": "https://<host>/mcp/sse"
    }
  ],
  "authentication": {
    "type": "jwt-bearer",
    "issuer": "https://<host>/auth",
    "audience": "sorcha-mcp",
    "acquisition_url": "https://github.com/Sorcha-Platform/Sorcha/blob/master/scripts/get-jwt-token.sh"
  },
  "tool_categories": {
    "admin": {
      "count": 13,
      "description": "Platform-administration tools — health checks, log queries, tenant and user management, validator status. Use this slice when an agent has admin scope."
    },
    "designer": {
      "count": 13,
      "description": "Blueprint authoring tools — create, validate, simulate, diff, export blueprints. Use this slice for workflow authoring agents."
    },
    "participant": {
      "count": 10,
      "description": "Participant workflow tools — submit actions, query the inbox, sign transactions, query the register. Use this slice for end-user-facing agents."
    }
  },
  "tool_catalogue_url": "https://<host>/api/mcp/tools",
  "documentation_url": "https://github.com/Sorcha-Platform/Sorcha/blob/master/docs/mcp-server.md"
}
```

**Constraints**:

- `version` MUST equal the OpenAPI document's `info.version` (FR-046, single canonical source).
- All counts in `tool_categories` MUST equal the actual tool counts derived at startup from the MCP server's tool registry.
- `description` field anywhere in the manifest MUST NOT contain marketing-adjective deny-list words.

### 3. MCP tool catalogue entry (served from runtime tool registry)

Wire format: JSON array, served at `/api/mcp/tools`. Each entry:

```json
{
  "name": "BlueprintCreate",
  "category": "designer",
  "description": "Creates a new Sorcha blueprint from a JSON or YAML document. Use when an agent has finalised a blueprint design and wants to register it for the first time; prefer `BlueprintUpdate` if the blueprint already exists at the given title.",
  "parameter_schema_url": "/api/mcp/tools/BlueprintCreate/schema"
}
```

**Constraints**:

- `description` MUST be at least 2 sentences.
- `description` MUST contain at least one disambiguating phrase (`call this when` / `use when` / `prefer this when` / `not when` / `versus` / `instead of` / `as opposed to`).

## Document records

### 4. `llms.txt` (repo root)

Plain text, ≤ 8 KB, [llmstxt.org](https://llmstxt.org) structure.

```text
# Sorcha
> <one-paragraph factual summary, single-line preferred>

## Capabilities
- <capability>: <one-line description>
- <capability>: <one-line description>
...

## Standards
- <name>: <stable spec URL>
- <name>: <stable spec URL>
...

## Links
- OpenAPI: <full URL of /.well-known/openapi.json>
- MCP manifest: <full URL of /.well-known/mcp.json>
- Quickstart: <repo URL>/blob/master/docs/quickstart.md
- Architecture: <repo URL>/blob/master/docs/architecture.md
- STANDARDS.md: <repo URL>/blob/master/STANDARDS.md
```

**Constraints**:
- File size ≤ 8192 bytes.
- Exactly one H1, exactly one blockquote summary paragraph.
- Sections `## Capabilities`, `## Standards`, `## Links` all present.
- Every `## Standards` entry name MUST match a `STANDARDS.md` row with status `full` or `partial`.
- No marketing-adjective deny-list words.

### 5. `docs/llms-full.txt`

Plain text, ≤ 32 KB. Sections: Architecture summary, Quickstart pointer, MCP integration pointer, Security model summary, How to integrate. A digest, not a duplicate, of the four published documents.

**Constraints**: same standards cross-reference and deny-list rules as `llms.txt`.

### 6. `STANDARDS.md` (repo root)

Markdown table. Single section.

```markdown
# Sorcha Standards Compliance

| Standard | Version | Body | Spec URL | Components | Status | Notes |
|---|---|---|---|---|---|---|
| BIP32 | 2017 | Bitcoin Improvement Proposals | [BIP-0032](...) | `src/Core/Sorcha.Wallet.Core/Services/Implementation/KeyManagementService.cs` | full | NBitcoin-backed |
| ... | ... | ... | ... | ... | ... | ... |

## Maintenance
...
```

**Column constraints**:
- `Status`: one of `full`, `partial`, `planned`.
- `Components`: each path in the cell MUST resolve to a real path in the repo (CI-enforced).
- `Notes`: required for any row whose `Status` is `partial` or `planned`.

### 7. Published technical documents (`docs/{architecture,openid4vc-haip-integration,applicability,security-model}.md`)

Markdown with YAML frontmatter:

```yaml
---
title: <Document Title>
description: <one-sentence factual summary>
standards:
  - <Standard 1>
  - <Standard 2>
last_updated: 2026-MM-DD
---
```

**Constraints**:
- Frontmatter present and parseable.
- `description` ≤ 200 characters.
- Every `standards[]` entry MUST match a `STANDARDS.md` row with status `full` or `partial`.
- `last_updated` is a valid ISO date.
- `last_updated` MUST be bumped when the document body changes (PR checklist).

### 8. `docs/quickstart.md`

Markdown. Sections: Prerequisites, Setup, Common failures, Verify your installation. Includes a copy-pasteable `curl` command and the expected JSON response shape.

### 9. `docs/mcp-server.md`

Markdown. Sections: Overview, Connecting (stdio + http+sse), Authentication, Role slices, Worked example transcript driving `walkthroughs/TradeFinance/`.

## C# models (new, under `src/Services/Sorcha.ApiGateway/Discoverability/Models/`)

These are the in-memory shapes that back the `/.well-known/mcp.json` endpoint serialisation.

### `McpManifest`

```csharp
public sealed record McpManifest(
    [property: JsonPropertyName("$schema")] string SchemaUrl,
    string Name,
    string Version,
    string Description,
    IReadOnlyList<McpTransport> Transports,
    McpAuthentication Authentication,
    IReadOnlyDictionary<string, McpToolCategory> ToolCategories,
    string ToolCatalogueUrl,
    string DocumentationUrl);
```

### `McpTransport`

```csharp
public sealed record McpTransport(
    string Type,                       // "stdio" or "http+sse"
    string? Command = null,            // populated for stdio
    IReadOnlyList<string>? Args = null, // populated for stdio
    string? Url = null);               // populated for http+sse
```

### `McpAuthentication`

```csharp
public sealed record McpAuthentication(
    string Type,                       // "jwt-bearer"
    string Issuer,
    string Audience,
    string AcquisitionUrl);
```

### `McpToolCategory`

```csharp
public sealed record McpToolCategory(
    int Count,
    string Description);
```

**Serialisation**:
- `System.Text.Json` with `JsonNamingPolicy.SnakeCaseLower` for property names.
- All records are immutable; populated once from `appsettings.json` configuration plus the live tool count read at startup.
- No request DTOs — these endpoints are read-only.
