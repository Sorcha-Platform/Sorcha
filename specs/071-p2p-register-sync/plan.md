# Implementation Plan: P2P Register Replication — End-to-End Transaction Sync

**Branch**: `071-p2p-register-sync` | **Date**: 2026-03-28 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/071-p2p-register-sync/spec.md`

## Summary

Enable two NAT'd Sorcha peers to subscribe to each other's registers and sync transactions through the PeerRouter (n0.sorcha.dev) acting as a streaming relay. The existing `PeerCommunication.Stream` bidirectional gRPC RPC is upgraded from UNIMPLEMENTED to a reverse-stream relay — NAT'd peers hold outbound streams to the Router, which pushes messages down those streams. Register advertisements are fixed in the Router's heartbeat processing. A new `DocketFinalizationService` verifies validator signatures on replicated dockets and writes sealed transactions to the local Register Service via the existing `WriteDocketAsync` API.

## Implementation Phases

### Phase 1: PeerRouter Streaming Relay (US1 — enabler)

**Goal**: Implement the `Stream` RPC on the Router so NAT'd peers can hold reverse streams.

1. Create `ReverseStreamManager` — thread-safe `ConcurrentDictionary<string, ReverseStreamEntry>` tracking active streams per peer ID
2. Implement `RouterCommunicationService.Stream()` — read loop dispatches incoming messages; registers the response writer in `ReverseStreamManager`
3. Modify `RouterCommunicationService.SendMessage()` — when recipient has empty address, check `ReverseStreamManager` for active stream and push via `responseStream.WriteAsync()`
4. Add connection pooling for non-NAT'd recipients (reuse `GrpcChannel` instead of creating per-message)
5. Tests: stream establishment, message forwarding via reverse stream, stream cleanup on disconnect, concurrent streams

### Phase 2: Heartbeat Advertisement Fix (US2)

**Goal**: Fix the Router to store and relay register advertisements via heartbeats.

1. Add `RoutingTable.UpdateAdvertisedRegisters(peerId, advertisements)` method
2. Modify `RouterHeartbeatService.ProcessHeartbeat()` — extract `request.AdvertisedRegisters` and call the new method
3. Modify `RouterHeartbeatService` response builder — aggregate other healthy peers' advertisements and include in response
4. Tests: advertisements stored on heartbeat, advertisements relayed to other peers, advertisement updates on version change

### Phase 3: Peer Service Reverse Stream Client (US1 + US3)

**Goal**: Peer Service establishes and maintains a reverse stream to the seed node (Router).

1. Modify `RelayCommunicationService` — add `EstablishReverseStreamAsync()` using `StreamingCommunicationClient` pattern
2. Background receive loop reads from response stream, dispatches to `RelayMessageHandler`
3. Reconnection with exponential backoff (2s → 60s max)
4. Keepalive ping every 30 seconds
5. Modify `RegisterSyncBackgroundService` — establish reverse stream on startup before processing subscriptions
6. Tests: stream establishment, reconnect after disconnect, keepalive timing, message dispatch

### Phase 4: Docket Finalization Service (US4 + US6)

**Goal**: Verify and finalize replicated dockets to Register Service storage.

1. Create `ValidatorKeyCache` — extracts and caches validator public key from genesis docket per register
2. Create `DocketFinalizationService`:
   - Recompute docket hash via `DocketHasher.ComputeDocketHash()`
   - Verify signature via `Sorcha.Cryptography` (supports ED25519, P-256, RSA-4096)
   - Verify chain integrity (PreviousHash linkage)
   - Call `IRegisterServiceClient.WriteDocketAsync()` for finalization
   - Idempotent writes (duplicate docket = success)
3. Integrate into `RegisterReplicationService` — call finalization after dockets are cached during initial sync
4. Integrate into `RelayMessageHandler` — call finalization when live docket notifications arrive
5. Tests: valid signature → finalized, invalid signature → rejected, chain break → rejected, Register Service down → retry, idempotent writes, genesis key extraction

### Phase 5: Live Transaction Streaming (US5)

**Goal**: After initial sync, live transactions and dockets propagate via the relay in near-real-time.

1. Verify existing `SubscribeToLiveTransactionsAsync` works over the reverse stream relay (it should — relay is transparent to the calling code)
2. Modify `RelayMessageHandler` — on `TransactionNotification` for subscribed register, trigger finalization check (is there a new docket?)
3. Handle stream catch-up after disconnect — pull dockets with version > last synced
4. Tests: live transaction arrives and is finalized, stream disconnect and catch-up, ordering guarantees

### Phase 6: Integration Testing & Deployment

**Goal**: End-to-end verification with two Docker instances through n0.sorcha.dev.

1. Deploy PeerRouter to Azure with `PEERROUTER__ENABLE_RELAY=true`
2. Configure two Docker Compose stacks with different `PeerService__NodeId` values
3. Verify: peer registration → heartbeat advertisements → register discovery → subscription → full sync → finalization → live streaming
4. Verify: data queryable on subscribing peer's Register Service
5. Verify: peer restart recovery (finalized data survives, subscription resumes)
6. Document results in walkthrough

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| Use existing `Stream` RPC (no proto changes) | Proto already defines bidirectional streaming; avoids breaking changes |
| Reverse stream (not polling) | PeerRouter is lightweight on Azure; streaming avoids memory pressure from message queues |
| Docket = finality signal | Matches blockchain semantics; transactions only persist when sealed by validator signature |
| `WriteDocketAsync` for finalization | Existing API; respects service boundaries; Register Service handles its own persistence |
| Validator key from genesis docket | No separate key exchange needed; genesis is always the first docket synced |
| Single validator model | Simplest path to working replication; distributed consensus is a future feature |
